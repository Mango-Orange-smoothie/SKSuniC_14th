# 1부. 무엇을 검증하려 했나

저희가 만든 건 **티어표**입니다. "이 인자가 이 불량의 원인이고, 얼마나 확실하다"를 11줄로 적은 표입니다.

문제는 이겁니다. **표를 만드는 것과, 그 표가 맞다는 걸 보이는 건 다른 일입니다.**
그래서 표를 만든 뒤에 표 자체를 시험했습니다.

```
① 두 관문이 정말 서로 다르게 작동하는가
② RF 가 떨어뜨린 인자는 왜 떨어졌는가
③ 이 표가 틀린 것도 잡아내는가
④ 기준이 아무거나 통과시키지는 않는가
⑤ 멘토 답을 받아놓고 푼 것 아닌가
⑥ 설정을 바꾸면 결론이 바뀌는가
```

# 2부. 표를 어떻게 만들었나

```
후보 선정 → 라벨 → 기준선 → 통계검정 → RandomForest → 재현성 → 경계값 → 등급
```

## 2-1. 후보를 데이터가 만들지 않았습니다

39개 센서 열이 있고 4개 불량이 있습니다. 조합하면 156개입니다.
이 156개를 다 뒤져서 통과한 걸 원인이라고 부르면 **낚시**입니다. 156번 던지면 우연히 걸리는 게 생깁니다.

그래서 **멘토님이 확정해주신 11쌍만** 후보로 뒀습니다. 나머지는 통과해도 원인이라고 부르지 않습니다.

## 2-2. 라벨 — 무엇을 "불량"으로 셀 것인가

**2세대와 3세대를 가른 유일한 변경입니다.**

원본 데이터에는 `NG_Code`라는 열이 있는데, 이 열은 **한 행에 불량 이름을 하나만** 붙입니다.
두 불량이 같이 나면 우선순위가 높은 쪽만 남고, 밀린 쪽은 표본에서 사라집니다.

| 불량 | NG_Code 기준 | 실제 발생 (이진) | 배수 |
|---|---:|---:|---:|
| Chipping | 24,175 | 24,175 | 1.00배 (안 밀림) |
| Remain_Coat | 9,266 | 9,774 | 1.05배 |
| Particle | 11,296 | 21,371 | **1.89배** |
| Micro_Crack | 4,921 | 15,413 | **3.13배** |

**Micro_Crack은 3분의 2가 사라지고 있었습니다.**

여기에 더 나쁜 게 겹쳐 있었습니다. 저희는 원래 *pure 라벨*을 썼습니다 — 다른 불량이 같이 난 행은
아예 불량군에서 빼는 방식입니다. 섞인 걸 빼야 깨끗하다고 생각해서였습니다.

그런데 **한 원인이 두 불량을 동시에 일으키면, 그 관계를 증명하는 행이 정확히 "같이 난 행"입니다.**

```
Cooling Failure   →  Micro_Crack + Chipping   같이 남
Cleaning Failure  →  Particle + Remain_Coat    같이 남

실측 — 위험구간에서 다른 불량을 동반한 비율
   CLN_Flow ↔ Particle          88%
   Cooling_Flow ↔ Micro_Crack   85%
   CLN_Pressure ↔ Particle      77%
```

**증거만 골라서 지우고 있었던 겁니다.** 그래서 3세대에서 라벨을 고쳤습니다.

```
Micro_Crack · Particle    → 이진 라벨  (해당 컬럼이 1이면 전부 불량으로 센다)
Chipping · Remain_Coat    → pure 유지  (밀리지 않으므로 바꿀 이유가 없다)
비교군                     → 전 defect 공통으로 '확실한 정상품' 만
```

> **왜 Chipping은 안 바꿨나**
> 배수가 1.00배입니다. 단일 라벨이 항상 대표로 잡아주므로 바꿀 이유가 없습니다.
> 그리고 실제로 바꿔보니 `Head_Temp`가 RF 상위 25%에서 밀려 **T1에서 내려갔습니다.**
> 필요 없는 변경으로 멀쩡한 판정을 잃을 뻔했습니다.

비교군도 같이 고쳤습니다. 예전엔 "그 불량이 아닌 행 전부"를 비교군으로 썼는데,
그러면 **불량군에서 뺀 행이 비교군으로 넘어갑니다.**
크랙이 있는 15,413행 중 10,552행이 "크랙 없음" 쪽에 들어가 있었습니다.
이제는 **확실한 정상품만** 비교군으로 씁니다.

## 2-3. 기준선 — 39개를 같은 자로 재기

온도는 42℃, 압력은 300, 유량은 10입니다.
**단위가 다르면 어느 게 더 많이 벗어났는지 비교할 수 없습니다.**

```
z = ( 그 샷의 값 − 같은 조건 정상품의 중앙값 ) / ( MAD × 1.4826 )

같은 조건 = Product_ID × Recipe_ID   →   54개 층으로 나눠서 각각 계산
```

층을 나누는 이유는 **제품과 레시피가 다르면 정상값 자체가 다르기 때문**입니다.
다 섞어서 하나의 기준을 쓰면, 원래 온도가 높게 도는 레시피가 통째로 "이상"으로 찍힙니다.

그리고 **평균이 아니라 중앙값**을, **표준편차가 아니라 MAD**를 씁니다.
평균과 표준편차는 극단값에 끌려갑니다. 즉 **불량이 기준선을 오염시킵니다.**

| 인자 | 정상품 중앙값 기준 | 전체 평균 기준 | 산포 차이 |
|---|---:|---:|---:|
| `Laser_Power` | 18.230 · σ 0.210 | 17.892 · σ 0.548 | **+161%** |
| `Power_Efficiency` | 94.493 · σ 0.399 | 92.784 · σ 2.108 | **+428%** |

> 산포가 4배로 부풀면 웬만한 이탈은 "정상 범위"가 됩니다.
> 실제로 이 방식으로 바꾸면 **`CLN_Flow`의 경보가 켜짐에서 꺼짐으로 뒤집힙니다.**

## 2-4. 관문 1 — 통계검정

**"불량일 때와 정상일 때, 이 인자 값이 실제로 다른가."**

Mann-Whitney U 검정을 쓰고 결과를 **Cliff's delta**로 바꿨습니다. −1에서 +1 사이 값인데 뜻이 직관적입니다.

> delta **0.936** = 불량 샷 하나와 정상 샷 하나를 무작위로 뽑았을 때,
> **약 97%에서 불량 쪽 값이 더 높다**

합격선은 두 개입니다. **p값 0.05 미만, 그리고 |delta| 0.2 이상.**
0.2는 Romano 2006에서 0.147 미만을 negligible, 0.33 미만을 small로 보는 관례 사이에서
팀이 합의한 값입니다.

그리고 **39열 × 4불량 = 156번** 검정하면 우연히 유의해지는 게 생깁니다.
그래서 **BH-FDR 보정**을 걸었습니다.

## 2-5. 관문 2 — RandomForest 순열중요도

**"나머지 38개를 다 알고 있어도, 이 인자가 여전히 필요한가."**

39개를 다 넣고 모델을 학습시킵니다. 그다음 **한 열만 골라 값을 무작위로 섞습니다.**
섞으면 그 열의 정보가 파괴됩니다. 그때 예측이 얼마나 무너지는지를 잽니다.
많이 무너지면 그 열이 중요했던 겁니다. 이걸 10번 반복해 평균을 냅니다.

합격선은 **상위 25%(39개 중 10위)**입니다. **이 25%는 근거가 없는 임의값입니다.** (8부 참조)

성능은 정확도가 아니라 **PR-AUC**로 쟀습니다.

| 불량 | 불량률 | RF 정확도 | "전부 정상" 찍기 | RF PR-AUC | 찍기 |
|---|---:|---:|---:|---:|---:|
| Chipping | 12.09% | 96.4% | 87.9% | **0.911** | 0.121 |

**정확도로 재면 4개 불량 중 3개에서 모델이 "전부 정상이라고 찍기"보다 낮게 나옵니다.**

## 2-6. 관문 3 — 재현성

같은 결과가 **원본 데이터셋과 r1 데이터셋에서 따로 나오는지** 봤습니다. 방향이 같으면 통과입니다.

## 2-7. 경계값 — 어디부터 위험구간인가

여기까지는 "관계가 있다/없다"입니다. 현장에 쓰려면 **"몇 도부터 조치해야 하나"**가 나와야 합니다.

```python
DecisionTreeClassifier(max_depth=1, class_weight="balanced")
```

깊이가 1인 나무입니다. 분할선을 딱 하나만 긋습니다.

```
Head_Temp  →  경계 42.646
              정상구간  41.52 ~ 42.49   불량률  0.37%
              위험구간  42.75 ~ 46.29   불량률 35.32%
                                        →  94.67배
```

이게 저희가 계속 인용하는 **94.67배의 출처**입니다.

> **이 방법의 구조적 결함 — 그리고 그 대비책**
>
> stump는 **어떤 열을 넣어도 무조건 선을 하나 긋습니다.** 관계가 전혀 없어도 긋습니다.
> 그러니 "경계값이 나왔다"는 사실 자체는 아무 증거가 못 됩니다.
>
> 그래서 **긋고 난 뒤에 검사**합니다 — `위험구간 불량률 > 정상구간 불량률`이 아니면
> 그 경계값은 못 씁니다. 코드가 `alert_usable = False`를 찍고 **경보를 차단**합니다.

실제로 하나가 걸렸습니다. `Cooling_Water_Temp`는 위험구간 7.50%, 정상구간 7.79%로 **거꾸로**입니다.
이 경계값으로 경보를 걸면 멀쩡한 장비를 세우게 됩니다. (5부)

## 2-8. 등급

```
세 관문 다 통과            →  T1  즉시조치      5건
두 관문 중 하나만 통과      →  T2  조건부조치    4건
도메인과 데이터가 반대      →  T4  판단보류      1건
원인이 아니라 결과          →  M1  감시지표      1건
```

**이 판정은 사람이 안 합니다.** 코드 다섯 줄이 합니다.

## 2-9. 원인 트랙과 감시지표 트랙

표에 `Surface_Roughness`가 있습니다. **11건 중 신호가 가장 강합니다** —
delta +0.628, RF 1위, 재현성 통과. 세 관문을 전부, 그것도 최고 점수로 통과했습니다.

그런데 T1이 아니라 **M1**입니다. 조치 대상이 아닙니다.

이유는 데이터가 아니라 **그 열이 무엇인가**에 있습니다.

```
FDC        설비가 제어하는 값     레이저 출력 · 헤드 온도 · 세정 압력 …
Response   가공 후 계측된 결과값   커프 폭 · 표면 거칠기 · 코팅 두께 …
```

`Surface_Roughness`는 **Response**입니다.
표면 거칠기가 파티클을 만드는 게 아니라, **파티클이 붙어서 거칠어진 것**입니다. 인과의 방향이 반대입니다.

> 이걸 원인으로 두면 **"거칠기를 낮추세요"**라는 말도 안 되는 조치가 나갑니다.
> 만질 수 있는 손잡이가 아니니까요.

그래서 트랙을 아예 분리했습니다. Response 열은 아무리 신호가 세도 **조치 지시를 내지 않고,
감시와 경보만** 합니다. 신호가 강하다는 사실은 그대로 쓸모가 있습니다 —
파티클이 늘고 있다는 걸 **가장 먼저 알려주는 지표**이기 때문입니다.

# 3부. 검증 ① — 두 관문이 정말 다르게 작동하는가

"통계검정도 하고 머신러닝도 했습니다"는 **말**입니다. 증명이 아닙니다.
둘이 똑같은 답을 낸다면 하나만 쓴 것과 다를 게 없으니까요.

그래서 **두 관문의 판정이 갈린 줄이 있는지** 표를 뒤졌습니다. 두 줄이 나왔습니다.

| 인자 → 불량 | 통계검정 | RandomForest |
|---|---|---|
| `Cooling_Flow` → Chipping | **통과** −0.512 | **불합격** (합격선 밖) |
| `CLN_Flow` → Particle | **미달** −0.150 | **통과** 2/39위 |

**정확히 반대로 갈렸습니다.**

두 번째 줄을 보면 왜 이런 일이 생기는지 알 수 있습니다. `CLN_Flow`의 delta는 −0.150으로 기준 미달입니다.
그런데 **경계값 아래로 내려가면 파티클이 9.16%에서 35.94%로 뜁니다. 3.92배입니다.**

Cliff's delta는 **두 집단 전체를 줄 세워** 비교합니다. 대부분 구간에서 겹치면 값이 작아집니다.
반면 트리는 **구간을 잘라서** 봅니다. "문턱 아래에서만 터진다"를 잡아냅니다.

> **한쪽만 썼으면 각각 하나씩 놓쳤습니다.** 이게 두 관문을 둔 이유의 증명입니다.

# 4부. 검증 ② — RF가 떨어뜨린 인자는 왜 떨어졌나

`Cooling_Flow`가 떨어진 게 **모델이 틀린 건지, 맞는 건지** 확인해야 했습니다.

가설은 **매개변수**였습니다. 냉각 유량이 치핑에 직접 작용하는 게 아니라 헤드 온도를 거쳐서
작용한다면, 헤드 온도를 이미 아는 모델에겐 냉각 유량이 쓸모없습니다.

```
Cooling_Flow 와 Head_Temp 의 상관   −0.422 (합본) · −0.527 (r1)

냉각유량 5분위  →  헤드온도 중앙값
    9.837       →     42.349     ← 유량 최저
    9.927       →     42.099
    9.985       →     42.063
   10.041       →     42.044
   10.120       →     42.028     ← 유량 최고
```

**유량이 낮을수록 헤드 온도가 단조적으로 올라갑니다.** 가설이 맞았습니다.

그리고 중요한 게 하나 더 있습니다. 멘토님 SOP 원문에 이렇게 적혀 있습니다.

> chiller에서 나오는 물의 온도 또는 water flow가 비정상적인 경우 head temp 열화를 일으키고,
> 높아진 head temp에 의해 laser beam의 shape/centering 등이 틀어진다

**멘토님은 우리 상관계수를 보고 쓰신 게 아닙니다. 우리는 상관을 잴 때 SOP를 보고 잰 게 아닙니다.**
둘이 따로 같은 구조를 가리켰습니다.

그래서 `Cooling_Flow`를 지우지 않고 T2로 남겼습니다.
조치는 인자별로 내지 않고 **칠러 계통 하나**로 냅니다.

> ⚠️ **문구 주의** — "39개 중 39위, 꼴찌"라고 말하면 안 됩니다.
> 중요도가 사실상 0이라 **0 근처끼리의 순위는 설정에 따라 14~39위로 흔들립니다.**
> 백업 자료의 깊이 스윕 표와 모순이 생깁니다. **"합격선 밖"**은 어떤 설정에서도 참입니다.

# 5부. 검증 ③ — 이 표가 틀린 것도 잡아내는가

통과한 것만 있는 표는 증명이 안 됩니다. **떨어뜨릴 수 있어야 기준입니다.**

```
Cooling_Water_Temp → Micro_Crack

도메인    수온이 오르면 크랙이 는다
데이터    delta −0.0066              ← 부호가 반대
          p 0.271                    ← 11건 중 유일하게 유의하지 않음
          위험구간 7.50% vs 정상 7.79%  ← 0.96배, 역전
```

2-7절의 검사에 걸려 **경보가 차단**됐습니다.

다만 지우지는 않았습니다. 확인해보니 이 값은 **89일 내내 약 1℃ 안에서만** 움직였습니다.

```
DP01  22.004     DP02  22.000     DP03  22.003     DP04  22.000
```

**움직이지 않은 변수는 "영향이 없다"가 아니라 "확인할 수 없다"입니다.**
멘토 확정 도메인이라 목록에 남기고 판단을 보류했습니다.

> 저희 규칙은 이겁니다. **데이터는 도메인을 강등시킬 수는 있어도 삭제하지는 못한다.**

# 6부. 검증 ④ — 기준이 아무거나 통과시키지는 않는가

가짜 인자 세 개를 만들어 진짜 39개와 **같은 판에 넣고 경쟁**시켰습니다.

```
① 표준정규 난수
② 균등 난수
③ Head_Temp 의 실제 값을 그대로 쓰되 순서만 무작위로 섞은 것
```

세 번째가 제일 엄격합니다. **분포는 완전히 똑같고 관계만 파괴**돼 있으니까요.

| 가짜 인자 | Chipping | Micro_Crack | Particle | Remain_Coat |
|---|---:|---:|---:|---:|
| 표준정규 난수 | 40/42 | 28/42 | **14/42** | 27/42 |
| 균등 난수 | 26/42 | 36/42 | 26/42 | 26/42 |
| `Head_Temp` 섞음 | 28/42 | 32/42 | 27/42 | 30/42 |

```
합격선 = 상위 10위
기회 12번 (가짜 3 × 불량 4)   →   통과 0번
가장 높이 올라간 가짜 = 14위
통계검정 쪽도 전부 |delta| < 0.009   (합격선 0.2)
```

**가짜는 두 관문 모두에서 한 번도 못 뚫었습니다.**

## 같이 나온 것 — 이건 반대 방향입니다

같은 스크립트로 **진짜 39개 전부에 같은 기준**을 걸어봤습니다.

| 불량 | 통계 통과 | RF 통과 | 두 관문 다 |
|---|---:|---:|---:|
| Chipping | 20/39 | 10/39 | **10/39** |
| Micro_Crack | 20/39 | 10/39 | **10/39** |
| Particle | 9/39 | 10/39 | 2/39 |
| Remain_Coat | 5/39 | 10/39 | 5/39 |

Chipping은 39개 중 10개가 통과합니다. 그중 멘토 확정은 3개뿐이고
`Kerf_Width_Profile` 같은 게 같이 붙어 있습니다.

**즉 통계와 RF만으로는 못 거릅니다.** 도메인 게이트가 실제로 일을 하고 있습니다.

> 이걸 "우리 기준이 엄격하다"로 쓰면 거짓말입니다. 정확한 해석은 이겁니다 —
> 데이터만 보면 Chipping 원인 후보가 10개 나옵니다. 우리는 3개만 원인이라고 부릅니다.
> **데이터가 허용하는 것보다 적게 주장하고 있습니다.**

# 7부. 검증 ⑤ — 멘토 답을 받아놓고 푼 것 아닌가

가장 아픈 질문입니다. **11쌍을 멘토님이 주셨는데, 그럼 분석이 왜 필요한가.**

그래서 도메인을 **모르는 척하고** 데이터만으로 39개를 줄 세웠습니다.
RF 순위 계산에는 도메인 정보가 한 글자도 안 들어갑니다.

```
── Remain_Coat                    ── Particle
   1위  CLN_Flow          ★          1위  Surface_Roughness  ★
   2위  CLN_Pressure      ★          2위  CLN_Flow           ★
   3위  Surface_Roughness            3위  CLN_Pressure       ★
   4위  Cleaning_Load_Ratio          4위  Cleaning_Load_Ratio

멘토 확정 11쌍 중   상위  3위 이내   7건
                   상위 10위 이내   8건
```

> 답을 받아서 푼 게 아니라, **따로 풀어도 같은 곳에 도착했습니다.**

못 잡은 것도 있습니다.

```
Chipping      Power_Efficiency 2위 · Laser_Power 3위 · Head_Temp 8위 · Cooling_Flow 22위
Micro_Crack   Cooling_Flow 23위 · Cooling_Water_Temp 31위     ← 둘 다 실패
```

`Cooling_Flow`가 낮은 건 4부의 매개 구조 때문입니다.
Micro_Crack 두 건은 그냥 못 잡았습니다. 감시 데이터에 크랙이 41건뿐이라 신호가 안 잡힙니다.

# 8부. 검증 ⑥ — 설정을 바꾸면 결론이 바뀌는가

**나무 깊이를 3부터 무제한까지** 바꿔봤습니다.

```
11건 중 10건은 판정이 그대로
흔들린 1건 = Head_Temp  (순위 5 → 7 → 8 → 11 → 10, 합격선 10위 근처)
```

`Head_Temp`만 경계에서 흔들립니다. 그런데 이 인자는
**통계검정에서 delta +0.936, 위험구간 불량률 94.67배**입니다.
RF 순위와 무관하게 유효인자입니다. **두 관문을 둔 게 여기서 보험이 됐습니다.**

**중요도 계산 방식도** 바꿔봤습니다. 트리 내장 중요도(gini)와 순열중요도로 각각 재봤더니
**11건 전부 합격/불합격이 같았습니다.**

> ⚠️ "순열중요도를 써서 결과가 달라졌다"고 말하면 **거짓말**입니다.
> 정확히는 **"두 방식으로 다 재봤고 결론이 같았다"**입니다.

# 9부. 검증이 못 한 것

**검증의 결론은 "다 맞다"가 아닙니다.**

## T1 다섯 건 중 세 건은 재현 검증을 못 받았습니다

```
Power_Efficiency → Chipping    판정불가
Laser_Power      → Chipping    판정불가
Head_Temp        → Chipping    판정불가
```

이유는 **원본 데이터에 순수 Chipping 표본이 3건뿐**이라서입니다. 검정을 돌릴 수가 없습니다.

"실패한 것"과 "못 돌린 것"은 다릅니다. 그래서 상태값을 네 개로 쪼갰습니다.

```
통과 / 판정불가(원본 표본부족) / 실패(데이터셋간 불일치) / 실패(도메인과 불일치)
```

그리고 **판정불가는 T1으로 올렸습니다.** 이건 저희가 만든 예외입니다.
정당한 이유가 있지만, **최고 등급 5건 중 3건이 미검증이라는 사실은 그대로 남습니다.**

## Micro_Crack은 확정 원인이 0건입니다

크랙 41건으로는 어느 장비가 나쁜지 가려낼 수 없습니다.
기준을 50건으로 올려 시뮬레이션도 해봤는데, 게이트는 열리지만
장비 4대가 26~27%로 몰려서 **점수가 의미를 잃습니다.**

## 임의값이 네 개 남아 있습니다

```
Cliff's delta 0.2   ← 근거 있음 (Romano 2006)
RF 상위 25%         ← 근거 없음
재현성 최소 10건    ← 근거 없음
장비별 최소 50건    ← 근거 없음
```

|---|---|---:|---:|---|---|

## 눈여겨볼 두 줄

**`CLN_Pressure` → Particle**은 방향이 한 번 바뀐 적이 있습니다.
처음엔 "압력이 오르면 파티클이 는다"로 뒀는데, 그러면 같은 압력이 Remain_Coat와 **정반대 조치**를
요구하게 됩니다. 2026-08-06에 도메인이 정정되면서 두 불량 모두 "압력을 올리면 좋아지는"
같은 방향이 됐고, 상충이 사라졌습니다. **도메인이 바뀌면 표도 바뀝니다.**

**`Cooling_Flow` → Micro_Crack**은 표에서 유일하게 **두 데이터셋이 서로 반대**인 줄입니다.
원본 +0.048, r1 −0.284. 원본 표본이 41건뿐이라 어느 쪽을 믿을지 정할 수가 없습니다.
그래서 T2에 두고 조치는 칠러 계통으로만 냅니다.
