## 먼저 — `alert_usable` 버그 잡아주셔서 감사합니다

`per_defect[defect].alert_usable`을 넣은 이유가 정확히 그 케이스였습니다.
`CLN_Flow`는 defect마다 티어와 경계값이 다릅니다.

| defect | tier | threshold | risk_ratio | alert_usable |
|---|---|---|---|---|
| Remain_Coat | **T1** | 9.725 | **24.67** | True |
| Particle | **T2** | 9.722 | **0.80** | **False** |

인자 레벨만 보면 둘이 구분되지 않습니다. 저도 처음엔 최상위 `tier`에 T1만 남기는 버그가 있어서,
`per_defect`를 추가하면서 최상위 `tier`는 **가장 보수적인 값(T2)** 으로 내리도록 고쳤습니다.

**독립 검정으로 같은 결론 내주신 것도 확인했습니다** — Remain_Coat 후보 17개 중 `CLN_Flow` 통제 시
분리력 22~55% 상실, `CLN_Pressure`만 4.28 → 30.18. 서로 다른 방법으로 같은 답이 나왔습니다.

# 요청 1 — `Surface_Roughness` : **이미 들어 있습니다**

`agent_cause_factors.json`의 **`monitor_factors`** 키에 있습니다.
요청하신 `role` 필드도 이미 들어 있습니다.

```json
"monitor_factors": {
  "Surface_Roughness": {
    "role": "감시지표(Response)",
    "defects": ["Particle"],
    "actionable": false,
    "alert_usable": true,
    "tier": "M1",
    "risk_ratio": 378.38,
    "threshold_raw": 0.598,
    "normal_range": "0.53 ~ 0.60",
    "risky_range": "0.60 ~ 0.66",
    "testability": "검정 가능(이탈 충분)",
    "per_defect": { "Particle": { ... } }
  }
}
```

## 원인

`agent.py` · `build_health_index.py`가 키를 하나만 읽고 있습니다.

```python
# 현재
CAUSE_FACTORS = json.load(f)["cause_factors"]
```

```python
# 이렇게 바꾸시면 됩니다
with open(REL_DB / "agent_cause_factors.json", encoding="utf-8") as f:
    _db = json.load(f)
CAUSE_FACTORS   = _db["cause_factors"]      # 원인(FDC)  — 조치 대상
MONITOR_FACTORS = _db["monitor_factors"]    # 감시지표(Response) — 상태 표시
```

**구조는 제안하신 설계와 동일합니다.**

```
원인(FDC)          actionable=true   → "이걸 조정하세요"
감시지표(Response)  actionable=false  → "이게 나빠지고 있습니다"
```

`actionable` 플래그로 갈라 쓰시면 되고, `role` 문자열로 갈라 쓰셔도 됩니다.

## 의도적으로 뺀 게 아닙니다

`cause_factors`에서 뺀 건 **원인이 아니기 때문**이지, 쓰지 말라는 뜻이 아닙니다.
**Particle 건강도는 `Surface_Roughness`로 내시고, 조치 문구만 막으시면** 됩니다.

말씀하신 문구가 정확합니다 — **"원인 미확인, 표면조도로 감시 중"**

> 참고: `Surface_Roughness`는 결과 공변이 검증돼 있습니다(daeho님 검증1, 선행신호 잔존율 7.5%).
> **사후 탐지에는 유효하지만 예측에는 못 씁니다.** 경보 문구에 이 단서가 있으면 좋겠습니다.

# 요청 3 — `rel_28` Vibration : **제 값이 틀렸습니다. 제안하신 값으로 갑니다**

## ① 상한 — **0.2111 채택**

제 실수 두 가지를 인정합니다.

| 제 값 | 문제 |
|---|---|
| `upper_candidate_p99 = 0.2609` | **합본 200k 기준.** 감시 데이터 최댓값 0.2487이라 **영원히 안 울림** |
| `upper_original_p99 = 0.2066` | 89일 전체라 **열화 구간이 섞임** |

제안하신 **0.2111**(안정 구간 × OK샷 p99.9)이 맞습니다.
**4대가 0.2089~0.2117로 수렴**한다는 게 결정적입니다 — 동일 사양 장비니 그게 맞는 그림입니다.

기존 CUSUM 대비 **DP02 11일 · DP03 5일 빠른 경보**도 확인했습니다.

## ② 스키마 — **CUSUM 파라미터로 바꾸겠습니다**

제가 가정한 필드가 틀렸습니다. 아래로 교체하겠습니다.

| 삭제 | 신설 |
|---|---|
| `trend_window_days` | `cusum_K` (0.7σ) |
| `trend_slope_threshold` | `cusum_H` (4.5σ) |
| `upper_candidate_p99` | `upper_limit` (0.2111) |
| `upper_candidate_p999` | `upper_limit_source` (안정구간 × OK샷 p99.9, 4대 0.2089~0.2117 수렴) |
| | `trend_test` (Mann-Kendall) · `trend_alpha` (0.05) |
| | `spec_breach_rule` (일별 초과 샷 ≥ `binom.ppf(0.99, n, 0.001)`) |

**"해당 없음"으로 남기지 않고 스키마를 실제 구현에 맞추는 게 맞다고 봅니다.**
필드가 비어 있으면 나중에 누군가 채우려다 잘못 채웁니다.

## ③ 짝짓기 — **도메인 근거로 진행이 맞습니다**

`Chipping` pure 3건이라 재현 검증 불가 → **"실패"가 아니라 "판정불가"**입니다.

제 티어표도 같은 상황을 이렇게 처리했습니다.

```
repro_state = "판정불가(원본 표본부족)"     →  T1 유지
repro_state = "실패(데이터셋간 방향 불일치)"  →  강등
```

**둘을 구분한 이유가 이겁니다.** 표본이 없어서 못 잰 것을 실패로 처리하면
강한 인자가 부당하게 강등됩니다.

`domain_evidence = 멘토 확정`이므로 **그대로 진행하십시오.**

알람 자체는 **설비 상태**이므로 defect와 무관하게 울려야 합니다.

| defect | 근거 |

| **Micro_Crack** | **멘토 확정만. 데이터로는 확인 불가** |

## 원본 기준으로는 둘 다 검증이 안 됩니다

| | 상한(0.2111) 초과 구간 불량률 | 전체 | n |
|---|---|---|---|
| Micro_Crack | **0.000%** | 0.034% | **581샷** |

**원본에 불량 자체가 Micro_Crack 34건 / Chipping 3건뿐**이라 표본이 없습니다.
일 단위 상관도 각각 +0.089 / +0.068로 무의미한 수준입니다.

## 합본 lift 차이(4.82 vs 0.39)의 해석

**r1 시나리오 설계의 반영으로 보입니다.**

`rel_26_scenario_injection_check.csv`에서 확인했듯, 이 데이터셋은 특정 고장 시나리오만
주입돼 있습니다. 냉각 실패가 안 들어간 것처럼(`Cooling_Water_Temp` \|z\|>3 = 0.306%),
**"진동 → Micro_Crack"도 r1에 안 들어간 것**으로 보입니다.

> **"데이터가 반박했다"가 아니라 "확인할 데이터가 없다"입니다.**
> 확인이 안 된다고 멘토 확정 도메인을 빼면 안 됩니다.

## 그래서 제안하는 문구

```
Vibration 0.2111 초과
  ├─ "설비 진동이 기준을 넘었습니다. 정비 점검 필요"
  │      ← 항상. defect 무관
  ├─ "Chipping 관련 가능성"
  │      ← 멘토 확정 · r1에서 관계 확인 · 감시 데이터로는 검증 불가
  └─ "Micro_Crack 관련 가능성"
         ← 멘토 확정 · r1에서도 미확인 · 감시 데이터로도 검증 불가
```

> **"위험 증가"가 아니라 "관련 가능성"**입니다.
> 감시 데이터로 확인이 안 되는데 단정하면 안 됩니다.

`rel_28`에 **`evidence_level`** 열을 추가했습니다. 이 열 하나만 읽으시면 문구가 나옵니다.
`lift`도 **`lift_combined`(합본) / `lift_original`(감시 데이터)** 로 나눠 실었습니다.
